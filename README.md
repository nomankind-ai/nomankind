# nomankind

nomankind checks where a fact came from before an AI model learns it, and keeps the proof.

Models learn from the world, and every fact they take in came from somewhere. Today that somewhere is usually figured out later, if at all: audits try to trace what a model was trained on after the weights already hold it, and mostly they cannot. nomankind works the other way around. Before a fact can be learned from, its source is captured and hashed, three independent operators check it and sign, and the record is sealed with a timestamp. Only then is it offered to a model. Proof first, use second.

It starts with one area, the AI ecosystem, because that is where models fall behind fastest. A model is frozen at its training cutoff, but prices, rate limits, model behavior, and APIs keep changing. nomankind is a running, cited record of those changes: an append-only log of small facts, each verified by three operators who are neither the submitter nor a model provider, each hashed and sealed so any edit shows, and each dated so you can see how fresh it is.

Built on the [1F916 protocol](https://1f916.org) for agent identity and sealed logs. Learn more at [nomankind.ai](https://nomankind.ai).

## Primary use: feeding continual learners

The log is built first for models that train from it. A continual learner pulls every change since its last sync as a sealed delta stream, in the exact order it was sealed, so two models syncing from the same position take in the same sequence and can prove it. Facts that were overturned travel as explicit unlearn signals. Each fact carries its evidence and a last-confirmed date, so a learner can weight it, hold it, or skip it. A drift attestation lets independent operators certify in public that a model's beliefs still match the record. Every fact a learner takes from the stream arrives with its chain of custody complete: source hash, three signatures, seal time, reproduction counts where a predicate exists, and every dispute since. This is provenance of the slice a model learned from the log, not of its training set.

## Verifiable now, and empirical where it can be

Verified means three independent operators confirmed that the source says what the entry says (two while the trusted pool is still under ten operators), and the entry stays open to dispute forever. For a fact that rests only on a cited page, that is provenance, and the log says so. Anyone can check that offline with two files and one script: `npm run verify -- <entry.json> <log.json>` prints the schema version it checked against, then exits 0 when the entry checks out and 1 with the named diffs when it does not. Every export carries every event whole, because the record is released the moment it is sealed and there is no key that reaches further; the run prints `withheld 0` and goes on to every other check. (A fork that publishes a release window of its own gets hash-line events back — the payload withheld, the hash, the links and the seal all there — and they are checked as what they are: the chain links them, the seal's root is over them, and an edited one fails.) A bundle exported `--bounded` carries this entry's own events with an inclusion proof each instead of the whole log, and the run prints `bounded not_run=chain,exclusions,derived,attestations` beside the verdict, so an `ok` is read as the narrower sentence it is. The record verifies free, with or without a key, from the seal that covers it.

The application itself runs as a Cloudflare Worker with the log and everything derived from it in D1. `npm run dev` serves it locally, with a health endpoint at `/health` that reports whether the Worker booted and whether its database answers. Schema changes are numbered SQL files under `migrations/`, applied in name order by wrangler and never edited after merge.

Every merge to main deploys the demo environment at demo.nomankind.ai through the Deploy demo action, which typechecks, runs the tests, applies the D1 migrations, and only then puts the Worker live. An annotated tag `v<major>.<minor>.<patch>` on main deploys production at app.nomankind.ai, and the apex nomankind.ai, through the Deploy production action. Every pull request gets a preview version of the demo environment, and a comment carrying its URL, or the uploaded version id when Cloudflare generates no preview URL because the Worker implements a Durable Object. The actions need two repository secrets, `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`; no deploy is ever run by hand.

Verification is the floor. Every entry carries an evidence tier in its signed core. A stated entry rests on a document. An observed entry rests on a measurement: a metered price call, a probe to a rate limit, an endpoint returning its deprecation error, a reproduced model behavior. The submitter freezes the test and its receipt with the claim, validators first judge whether the test decides the claim and then run it themselves under a published n-of-k rule, and each records its own receipt. Behavior and misbehavior entries are observed by rule. A measured record earns standing beside the validation itself, so the operators who measure are credited above the operators who copy. That is the path from verification toward truth: where a claim can be measured, the record moves past "a source said it" toward "this was observed to hold," fact by fact. Where it cannot, the entry stays stated and honest about it. The tier tells a reader which kind of entry they are holding. A confidence field derived from the receipts is planned; it stays null until there is enough dispute history to calibrate it, and its raw inputs are exposed in the meantime.

## Also for frozen models

A model that reads at inference time gets the fastest true fact on wake: one signed entry with a receipt, no vendor page and no injection surface.

## The record outlives the source

Sources rot. Labs edit their own documentation quietly, pages move, and the page a fact came from can be changed or taken down. nomankind captures what a source said at the moment it was cited, hashes it, and seals it into a witnessed log. Even if the original page is later edited or destroyed, the sealed, dated, independently verified record of what it said still stands, and anyone can check it offline. A legal takedown can remove a served copy of a page, but not the hash, the signatures, or the proof of what it once said.

That guarantee reaches well past the AI ecosystem. The mechanism generalizes to any domain with checkable predicates, and degrades to provenance-only where they do not exist: who said it, what it said at capture, who confirmed it, when it was sealed. Take a work of art: if the piece is lost or destroyed, that same record, who made it, what it was, and who independently vouched for it, still stands on its own. nomankind keeps its scope narrow, the AI ecosystem, by design. New domains come only after this one is saturated.

The operator registry is served by the Worker: `POST /operators` to join, `POST /genesis` for the maintainer's one-time naming of the first trusted operators, and `GET /operators`, `GET /operators/{id}` and `GET /agents/{id}` to read the result. Joining takes the whitepaper's three steps — publish a TXT record at `_nomankind.<your domain>` carrying your 1F916 agent id, complete payout onboarding, and sign the independence attestation for the domain you are joining with your 1F916 key — and the DNS check is real everywhere, bounded like every other outbound call by `FETCH_TIMEOUT_MS` — the DNS-over-HTTPS lookup and the drand beacon read included, so a resolver or a chain endpoint that accepts the connection and never answers is `unavailable` or `beacon_unavailable` rather than a door or a sweep held open — while payout onboarding is mocked on demo until the payment provider is wired. The registration stores the connected account id the body carried as the operator's payout reference (D-053: that id and nothing else about the account). Nothing transfers against it and nothing ever will: the record is free and there are no payouts (D-127), so the reference is a column the door still writes and no step reads. The registration body carries the registered `domain` the operator joins first, and the attestation it signs is that domain's own sentence under that domain's version, both read out of the domain registry; a body naming no domain reads as `ai-ecosystem`, which is what a client written before schema v0.7 meant. The operator id is the domain itself, and it has to be a name: lowercase, at least two labels, no trailing dot, and neither an IP address — a dotted quad or a bracketed IPv6 form — nor a name whose last label is all digits, because an address is not something a TXT record can prove control of and not something a reader can look up to see who stands behind an operator. The attestation's own `signed_at` is held to `REQUEST_CLOCK_SKEW_SECONDS` of the request clock on all three doors — registering, joining a domain, binding an agent — and outside it the answer is 422 `bad_attestation`: on a first registration the request and the attestation are signed by the same key, so without the window one fresh signature would have stood for both, and a sentence signed years ago by a key that has since changed hands would still register an operator today. `GET /operators/{id}` lists the `domains` the operator is attested in, and `POST /operators/{id}/domains` takes on a later one: the body is `{domain, attestation}`, signed by one of the operator's own agents, and the refusals are 400 `bad_id` or `bad_body`, 401 for a bad request signature, 404 `not_found`, 403 `agent_mismatch` when the signing key answers for somebody else, then `unregistered_operator`, `unregistered_domain`, `excluded_party` (403), `already_joined` (409), `missing_attestation`, `bad_attestation` and `attestation_domain_mismatch`. Eligibility follows the attestation: an operator judges, reconfirms, requests a check of, or scores an attestation in a domain only where it has signed that domain's sentence, and the exclusion rule is that domain's own published party list rather than one global one — so an operator excluded in one domain stays eligible in another. The trusted pool itself stays global. Every write door rebuilds and retries when another write takes the log's next position first — two registrations in one tick, or a decision landing while the sweep seals — so the loser is answered on its merits (409 `operator_exists` for a name already taken) instead of being dropped; three rebuilds that all lose is 503 `chain_conflict`, which is its own refusal precisely because the database is answering fine. Locally, apply the migrations first with `npx wrangler d1 migrations apply nomankind-local --local`, because `npm run dev` starts on an empty local database and these routes answer 503 `storage_unreachable` until the schema is there.

Entries are submitted to the same Worker. `POST /entries` takes `{entry, receipt}`, where `entry` is the eighteen immutable core keys plus the author's `signature` over their JCS canonical form and `receipt` is the observation receipt object, sent only when the core carries an `observation`. The request itself is signed like every other write: the four `x-nomankind-*` headers carrying the agent id, a timestamp, a single-use nonce, and an Ed25519 signature over the method, the path and the canonical body. Every write door opens through one shared gate, in one order: the four headers' presence and shape and the timestamp's skew are checked on headers alone, so an unsigned body is refused without being read; then the body against `REQUEST_MAX_BODY_BYTES`, a declared `Content-Length` above it answering 413 `body_too_large` before a byte is read and a body that declares no length abandoned at the cap plus one; then the parse, which is the first `JSON.parse` anywhere on the write path; then the nonce and the signature; then one write charged against the day's two buckets, `WRITES_PER_AGENT_PER_DAY` keyed by the signing agent and `WRITES_PER_CLIENT_PER_DAY` keyed by the client address, answering 429 `write_quota` with `x-nomankind-write-limit` and `x-nomankind-write-remaining` when either is spent. Section 5 still lets anyone submit with a bare agent key; what the second bucket adds is that a key which costs nothing to mint no longer buys an unbounded number of fetches, archive writes and rows. A request that authenticated and is then refused on its own merits has still spent its nonce and its write. `POST /genesis` is the one door that charges none, because it is the maintainer's own key. Anyone may submit with a bare agent key, and the entry then names no operator; a key bound to a registered operator must name that operator in its signed core. The Worker fetches the citation itself under the norm-v1.2 rule — fixed headers, at most five redirects, a thirty-second timeout, the final URL recorded — and refuses the submission unless the hash of what it fetched is the `snapshot_hash` the author signed. Refusals are 401 for a bad request signature or a bad entry signature, 403 when the signing key is not the author, 409 for an entry already in the log, and 422 for everything the entry itself gets wrong: `core_too_large` naming the field, for a `claim`, `before`, `after` or `citation` longer than `CORE_TEXT_MAX_CHARS` or an `evidence` or `observation` whose canonical form is longer than `EVIDENCE_MAX_BYTES` — a door rule and not a schema change, so every entry already in the log stays valid, checked before anything is fetched; `snapshot_mismatch`, `needs_javascript` for a page whose content only a browser could show, `invalid_json`, `unsupported_citation`, the fetch refusals (`bad_status`, `too_large` — `CAPTURE_MAX_BYTES` is checked at the door on the bytes that came back as well as inside the fetch adapter, so the ceiling holds whichever fetcher a fork runs — `too_many_redirects`, `timeout`, `fetch_failed`), `transcript_shape` for a behavior or misbehavior entry whose `evidence` does not carry the six transcript keys — the shape is read before the hash is compared, so an evidence object missing a key is refused in the word that names it rather than as a `snapshot_mismatch` — `source_not_official` a second time when the capture's final URL earns a lower class than the citation did — an official host that redirects to a third party, or down to http, cannot carry an official-required category, while a redirect that stays on the host changes nothing — a supersession that does not hold, a missing or mismatched receipt, and `schema_invalid` with the failing fields. One of them is the duplicate (D-085): `duplicate_claim`, answered with `duplicate_of` naming the entry already in the log, when the same domain, subject, category, normalized value and `effective_at` is already live as a draft or a verified entry and this submission does not name that entry in `supersedes` — checked right after the supersession refusals and before the citation is fetched, so a duplicate costs the log no fetch and writes nothing, and because the dispute door runs this same pipeline a correction that duplicates a live correction of the same subject is refused the same way. `effective_at` is in the key because the rule the paper writes stops where judgment begins: "everything the key cannot decide — two entries saying the same thing in different words, or at a different `effective_at` — is a validator's judgment", so the same value filed as of another date is another claim, reaches the validators, and is rejected there in the published form if they read it as a restatement. The lookup is one indexed seek and not a scan of the subject's history: the rule's five fields are hashed into the entry's own `duplicate_key` column (migration 0019) by the one upsert every entry write goes through, so both doors ask the index for the newest live entry holding the key and apply the two exemptions it cannot know — an entry is never a duplicate of itself, and never of the entry it supersedes. A row whose key was not computed under the rule in force carries null and is invisible to the index — an entry written before 0019, and every entry at all after 0020 emptied the column so `effective_at` could join the key — so the sweep's `duplicates` step gives at most `DUPLICATE_BACKFILL_PER_RUN` of them their key each run — recomputed in code from each row's own signed core, because the norm rule is Unicode normalization and whitespace folding that SQL cannot run — and the next run continues until none is left, after which the step is one bounded read that finds nothing. Three of those refusals are the domain's: `missing_domain` for a seventeen-key core, which is what an entry sealed before schema v0.7 carried and which no new entry may — the body shape allows exactly that one key to be absent, so a core carrying every other field and no domain is told `missing_domain` rather than `bad_body`, which is the difference between a refusal an author can act on and one that says only that something was wrong — `unregistered_domain` for a slug the registry does not hold, and `category_not_in_domain` for a category outside that domain's own enum — the schema's category enum is the union of every registered domain's, and which of them a domain admits is the registry document's table. `domain` is part of the signed core rather than a field beside it, so an entry can never be re-homed: the id, the entry hash and the author's signature all cover it. A behavior or misbehavior entry is snapshotted differently — its `snapshot_hash` is over the frozen transcript, so nothing is fetched for it — but when its `evidence.provider_statement` is non-null, that page (which the schema requires to be the `citation`) is fetched under the same norm rule and archived beside the transcript under the capture role `statement`, refusing the submission with the same fetch and rule reasons if it cannot be pinned; the statement carries no signed hash to be compared against, so the capture is simply the record of what the provider's page said at the moment the claim was made. Nothing is written unless every check passes. On success the answer is 201 with the derived entry, which is `draft`: status is recomputed from the log and is never sent in.

**Sources.** A stated entry is verified when independent operators confirm the cited source said what the entry says. That checks the reading and not the source's standing to say it, so the domain registry publishes a source policy beside every other domain table, and the door enforces it (decision D-080). Each entry gets a class derived from its own citation — `official` when the host is one the subject's authority publishes under, `recognized` for an editorial, standards, court, regulator or journal host, `other` for everything else — computed by `sourceClassOf` from the domain, the subject and the citation, and carried in the sidecar as `source: {class, matched_host, authority}`. The host rule is exact: `https` only, the lowercased host equal to a listed host or a subdomain of it, so `docs.anthropic.com` matches `anthropic.com` and `anthropic.com.evil.tld` does not, and a port or userinfo makes it `other`. The authority is the subject's primary party: the first segment of the subject, lowercased, under the domain's `<provider>/<model or product>` convention. Categories whose claim has an authoritative source by nature — `pricing`, `limit`, `deprecation`, `release`, `outage` in `ai-ecosystem` — are gated rather than labeled: an entry in one of them must cite the subject's official source or it is refused 422 `source_not_official`, and 422 `unknown_authority` when the primary party has no row in the table at all, both before the citation is fetched and before anything is written. A dispute's correction entry goes through this same pipeline, but under its own category — `correction` is official-required nowhere — so the dispute door runs the gate a second time against the entry being challenged: after the filing rules and 409 `dispute_open`, before `bad_report_link` and before anything is archived or written, `checkSource` is asked about the target's domain and category with the correction's own subject and citation, and a correction of a pricing claim citing anything but the target subject's official source is refused 422 `source_not_official` (or `unknown_authority`). Nothing about the signed core changed: the citation was always in it, and the class is a reading of it, so no stored entry moves and no signature is affected. What the policy does not automate is the judgment — a validator's approval asserts that the cited page supports the claim — and the tables, the host rule and that sentence are all published at `/policy` and in `schema/nomankind-domain-registry-v1.md`.

**Domains.** Three domains are registered (decision D-096): `ai-ecosystem`, what models and AI products cost and do; `ai-governance`, the instruments states and intergovernmental bodies issue, in force, amended, repealed, guided or enforced; and `ai-safety`, what non-state parties committed to about harm to people and what their deployed systems and guardrail products actually do — one fact has one home, and the domain is in the signed core, so nothing can be moved between them afterwards. Both new domains publish a subject-authority rule beside their excluded-party list: an operator whose own domain is, or is under, an official host of the entry's subject's authority row may not validate it, reconfirm it or be drawn for it, refused 422 `subject_authority` on the validate and reconfirm doors and dropped from the draw, because the body that issued an instrument is the party the record is checking. `ai-safety`'s three observed categories may be submitted with the transcript's request payload replaced by the placeholder object `{"[REDACTED]": "sha256:<hex>"}`, and the body then carries `disclosure`: an object mapping each placeholder's RFC 6901 JSON pointer into the artifact to the value it replaced, refused 422 `disclosure_missing` for a placeholder with no pointer (or a `disclosure` body in a domain and category that publish no such rule) and 422 `disclosure_mismatch` when the value does not hash to the placeholder. The disclosure object is archived at its own content address under the capture role `disclosure`, and `GET /captures/{hash}` answers it 403 `undisclosed` with `disclose_after` — the entry's `submitted_at` plus the domain's published window — to an unsigned reader until that date, while a signed request from an agent bound to any registered operator is served throughout, because a validator has to reproduce the measurement; the transcript's own hash is taken over the artifact as submitted, placeholders included, so nothing about what the author signed depends on the payload being public. `ai-safety`'s four version-shaped categories name the version they were observed against as the subject's third segment — `<party>/<model>/<version>` — refused 422 `bad_subject_version` at submit when it is missing, and an entry in one of them goes stale the moment an entry about another version of the same model verifies, permanently: `POST /entries/{id}/reconfirm` refuses it 422 `version_stale`, because the version it observed is gone.

`GET /entries/{id}` returns that entry. The raw capture is public too: `GET /captures/{hash}` returns the bytes that were archived under a `snapshot_hash` or a `receipt_hash`, with the archive address in `x-nomankind-archive-hash`, and `GET /captures/{hash}/sidecar` returns the norm rule's `{final_url, status, headers, fetched_at, fetcher}` record of the fetch. A capture is served as evidence rather than as a page — its stored media type, but `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox` — because anyone can submit with a bare key and the bytes are a stranger's. The captures live in R2 under the `CAPTURES` binding — `nomankind-local-captures`, `nomankind-demo-captures`, `nomankind-production-captures` — content addressed and written once, so a capture is evidence rather than a cache.

## Validating, and the demo checkpoint

Decisions come in at `POST /entries/{id}/validate`, signed like every other write. The body is `{record, signature}`: `record` is exactly the schema's `approvers[]` item — agent, operator, decision, reason, snapshot_hash, assigned_random, test_accepted, reproduction, observation, signed_at — and `signature` is the validator's `nomankind-record-v1` signature over the entry id, the kind and the record, which sits beside the record rather than inside it because the schema has no field for it. The validator's own snapshot hash is the point: each validator fetches the live source itself, so the capture taken at submission is never the only witness to what the page said. Status is never sent in and never set: the entry that comes back is derived from a log that now holds this decision. Refusals are 400 `bad_id` or `bad_body`, 401 for a bad request signature, 404 `not_found`, 403 `agent_mismatch` when the key that signed the envelope is not the record's own, 409 `entry_closed` once the verdict stands, and then 422 for everything else, in the order the door checks it: `bad_signed_at`, `bad_record_signature`, `deadline_passed` when the operator answering was drawn for this entry and the draw's seventy-two hours have run out — read off the assignment the draw wrote rather than off an assignment the sweep has not closed yet, so a late decision gets the same answer whether or not a sweep has run since — and then the record's own rules in `VALIDATION_REFUSALS` order: `unregistered_agent`, `operator_mismatch`, `unregistered_operator`, `submitter_agent`, the six remaining exclusions of `src/eligibility.ts` (`submitter_operator`, `original_signer`, `maintainer_operator`, `provider_operator`, `subject_authority`, `operator_not_in_domain`), `missing_snapshot_hash`, `missing_reason`, `duplicate_operator`, `assigned_random_without_assignment`, `assignment_without_assigned_random`, then the evidence-shape refusals, and `schema_invalid` with the failing fields. Nothing is written unless every check passes. Judging an entry a duplicate is a rejection like any other, written in a published form: the reason `duplicate_claim:<entry id>`, naming the verified entry this one duplicates and does not supersede. The door takes it as it takes any reason and nothing new is signed, which is the point — the mechanical duplicate is the submit door's, and the judgment, two entries saying the same thing in different words, is the validators'; what the form buys is that the entry page links the id and the confidence inputs publish it. There are three answers, and the door takes all three: `approve`, which on an observed non-transcript entry the validator accepted the test for must carry that validator's own measurement (runs and holds), present and well formed (`missing_observation`, `bad_measurement`) — whether it passed is read later by derivation and standing, not at the door; `reject`, which needs a reason and may carry the measurement it found but is not required to, because a rejection can rest on the citation alone; and `test_accepted` false, the judgment that the proposed test does not decide the claim, recorded on a rejection and an approval alike so the majority can be counted. A negative result is a first-class answer and earns what a positive one earns: the standing for a completed validation is earned whichever way the decision went, and `STANDING_VALIDATION_REPRODUCED` is earned beside it for a record carrying a passing measurement — work, not a direction. A superseding entry names its target in its own frozen core, and the target's `superseded_by` is written into the target's stored row in the very same batch as the decision that verifies the superseder — never at submission and never on a decision that does not verify — so no reader ever sees a superseding entry verified and its target still standing.

Reconfirmations come in at `POST /entries/{id}/reconfirm`, signed the same way. The body is `{record, signature}` again: `record` is exactly the schema's `reconfirmations[]` item — agent, operator, snapshot_hash, reproduction, observation, signed_at, every key present and the unused ones null — and `signature` is the reconfirmer's `nomankind-record-v1` signature over the entry id, the kind `reconfirmation` and the record. Any trusted operator can refresh a stale entry, and only a trusted one; no agent under the submitter's own operator may, exactly as at validation. The attestation rests on a fresh snapshot hash the reconfirmer took for themselves, plus a fresh reproduction for a behavior or misbehavior entry and a fresh measurement for any other entry that verified as observed. Nothing derived is sent in: the entry that comes back is derived from a log that now holds the attestation, so `last_confirmed` advances to the record's date and the window reopens. The reconfirmer earns standing for the check, and nothing else is owed to anybody: no read of the entry was priced. Refusals are 400 `bad_id` or `bad_body`, 401 for a bad request signature, 404 `not_found`, 403 `agent_mismatch`, then 422 `bad_signed_at` and `bad_record_signature`, then 422 for everything the record itself gets wrong, in `RECONFIRMATION_REFUSALS` order — `entry_not_verified`, `version_stale`, `unregistered_agent`, `operator_mismatch`, `submitter_agent`, `submitter_operator`, `untrusted_operator`, `subject_authority`, `operator_not_in_domain`, `missing_snapshot_hash`, and the reproduction and observation shape refusals — then 409 `entry_not_stale` for an entry still inside its window (a check inside the window is a staked revalidation request, below), and `schema_invalid` with the failing fields. Nothing is written unless every check passes.

An operator can put a second key to work: `POST /operators/{id}/agents` takes `{agent, attestation}`, signed by an agent already bound to that operator and carrying the new agent's own signature over the operator's registration domain's sentence, and answers 201 with the operator record and its agents — refused 404 `unregistered_operator`, 403 `not_operator_agent` when the signing key answers for somebody else, 409 `agent_bound` for an agent already bound anywhere, and 422 `bad_agent`, `missing_attestation`, `bad_attestation` or `attestation_domain_mismatch` — with `npm run register -- <existing-key.json> <base-url> <operator-domain> --bind <new-key.json>` as the command for it; the DNS TXT record is not checked again, because it bound the first agent and the operator vouches for later ones by signing, and the new agent validates, reconfirms and scores for the operator exactly as the first does, under every exclusion that counts an operator.

`GET /events` pages the whole log: `?after=<seq>&limit=<n>` resumes strictly after a position the caller already has and answers `{events, head}`, so a reader knows how far behind they are. Those two are the whole query and anything else is 400 `bad_query` — a parameter this door does not take, a parameter given twice, an `after` that is not a position, or a `limit` above the published page size, which is refused rather than clamped, because a caller who asked for five hundred rows and was handed a hundred would believe they had seen them all. It is keyset paging, never offset, and the events go out exactly as they are stored, hash chain and all, because a reader who cannot recompute the chain cannot check anything. `GET /entries/{id}/events` is the same read narrowed to one entry (D-120): `{entry_id, head, events, proofs}`, the sub-sequence of the log bearing that id in seq order, with one proof per sealed event in exactly the shape `GET /events/{seq}/proof` answers and an unsealed event simply absent from `proofs`. Same window — a free reader inside it gets hash lines, a key or an operator signature is served whole, and the proofs go out either way — same bucket and the same three `x-nomankind` headers, one call one read; 400 `bad_id`, 404 `not_found`, 405 with `Allow: GET, HEAD`. It is bounded by the entry rather than by the log, which is what lets a reader gather one entry's whole story without paging the log to its head, and it is never held at the edge, because what it answers depends on who is asking. The sweep runs on a timer this project controls: a Durable Object (`src/worker/sweeper.ts`) whose alarm runs it every five minutes and then arms the next alarm, and any request to the Worker arms it if nothing is armed, so a broken chain of alarms is repaired by the next visitor. The cron trigger stays beside it as a watchdog rather than a second timer: every five minutes it arms the alarm if nothing is armed and sweeps nothing itself, so a chain of alarms broken by a run the platform killed mid-flight heals without waiting for a visitor, and an interval never carries two sweeps of the same log. Each run commits a pool snapshot when the trusted pool has moved, draws the one randomly assigned validator for each draft entry that owes one against a snapshot committed before the beacon round it uses, and marks an assignment missed once its seventy-two hours are up and draws a replacement. The draw skips every pool operator the validation door would refuse on that entry, by the same predicate derivation counts decisions with — the seven exclusions in one place, so a draw can never land on an operator that could only miss its seventy-two hours. Below ten trusted operators no draw is made at all and two approvals verify, which is what lets a small pool verify anything; either way the paper's precondition holds first — "three verified operators outside the submitter's own, and a non-empty trusted pool" — and the three are counted over the operators that could actually sign that entry, attested in its domain, not an excluded party of it and not under its subject's own authority, because a count of validators that cannot validate is not a count of validators. Then it rewrites the entries whose freshness window ran out overnight, appending no event, because a window closing is a fact about the calendar and the log rather than something anyone signs; the report names them under `staled`. The rewrite is for the counters, the index and the ledger's half shares, never for the reader: `stale` is the one derived field that depends on when it is asked, so the read and sync doors derive it at the door from `expires_at` against the request's own clock, and an entry past its window reads `"stale": true` the minute it is past — the same JSON before and after the sweep gets to it.

The same sweep then seals. Each run seals every event the last seal did not cover into one Merkle batch, chained to the seal before it, so drafts and rejections leave exactly the proof a verified entry does; it gathers countersignatures for the seals still waiting on the outside world, keeping one signature per operator and refusing any witness under the maintainer's operator or under nomankind's own agents; and it anchors one owed day's roots into an external timestamping chain. A seal covers at most two hundred events and its write — the seal row and one rewrite per entry it covers, because an entry carries the inclusion proof of its own submission — reaches the database in batches of a hundred statements rather than one batch the database may refuse; the seal row goes first, so a run the platform kills between two batches leaves a seal whose remaining rewrites the next run finishes, and a rewrite is the same derivation whether it is the first time or the second. The anchor is a backlog rather than yesterday alone: the days owed run from the day after the newest anchored one, or from the day the log was first sealed on, through yesterday, and each run takes the oldest still owed, so a day whose following day saw no sweep at all is anchored by the next run that does instead of never. A day inside that range with no seals is passed over and never anchored, because an anchor with no roots would be a claim about a day nothing was sealed on. Five reads serve what that makes: `GET /seals?after=&limit=` pages the seal chain and names its head, `GET /seals/{seq}` answers one seal, `GET /events/{seq}/proof` answers the inclusion proof for one event against its covering seal's root (404 `unsealed` while nothing covers it yet), `GET /anchors?after=&limit=` pages the daily anchors, and `GET /anchors/{date}` answers one day's. Both listings take `after` and `limit` and nothing else, and both refuse 400 `bad_query` for an unknown or repeated parameter or a limit outside the page size; the anchors' `after` and the date in the path are checked against the calendar rather than against a shape, so `?after=2026-13-45` is a refusal instead of an empty page about a day that does not exist. The witness set is per environment: local and demo run a published mock pair whose keys are in this repository and prove only that the plumbing ran, while production runs the founding 1F916 registry's pinned witnesses once nomankind's citizen is registered and `SEALING_AGENT_HANDLE`, `REGISTRY_CREDENTIAL` and `SEALING_AGENT_KEY` are set — without all three, production says the registry track is unavailable rather than putting invented signatures on a real seal. A seal's `registry` record names the `memory.seal` identity event that anchors its fingerprint — `event_id` and `event_hash`, resolved from `GET /api/record/<handle>` and never the registry's own seal row id, and `event_id` null until that record lists the event — because that event's leaf is what the countersignatures cover. The daily anchor is a local record on demo, which keeps the day's roots without an external receipt, and OpenTimestamps on production.

## Reading

`GET /read` is Section 8's frozen reader, in two forms. `GET /read/{id}` names an entry; `GET /read?subject=&category=` asks nomankind to choose the current answer about one subject in one category, with `min_tier=stated|observed`, `min_source=official|recognized` and `max_age=<whole days>` as the reader's three demands, `domain=<slug>` to answer from one registered domain, and `?entry_id=` as the query form of the first. A reader that names no domain gets every domain's entries about that subject as candidates, which is what a client written before schema v0.7 asks for. Only a verified entry is ever served, the tier compared is the effective one the entry actually verified at rather than the tier its signed core claims, the source class compared is the one the sidecar derived from the entry's own citation (official above recognized above other), and the age is whole UTC calendar days against `last_confirmed`, inclusive. A query is refused rather than quietly narrowed: 400 `unknown_parameter`, `repeated_parameter`, `bad_entry_id`, `mixed_query`, `missing_subject`, `missing_category`, `bad_category`, `unknown_domain`, `bad_min_tier`, `bad_min_source`, `bad_max_age`, in that order, so a reader who mistyped `min_tier` is told which rule refused them instead of being handed an answer that ignored their demand, and a parameter given twice is its own refusal because two values are two questions and picking one of them is guessing. `GET /read/{id}` names its entry in the path and takes no query at all, so a parameter on it is refused in the same two words rather than dropped: a demand this door cannot apply must not come back looking like a demand it met. Anything but GET is 405.

The answer is `{entry, sidecar, seal, receipt}`. `entry` is the stored derived entry exactly as `GET /entries/{id}` serves it, carrying its own `seal` object with the inclusion proof, the position and the witnesses; `sidecar` is the state the schema cannot hold, including the `effective_tier` the tier demand was judged against; `seal` is the seal record covering the entry's submission, which is what that inclusion proof recomputes against, and null while nothing has sealed it yet; and `receipt` is the signed read receipt — `entry_id`, `entry_hash` (the entry's core hash, so a receipt names the version that was served and not merely the entry), `read_at`, `counter`, `issuer`, `signature`. Verify it with `verifyReadReceipt` from `src/receipt.ts`: the signature is Ed25519 over `nomankind-read-receipt-v1\n` and the RFC 8785 canonical JSON of the five fields, checked against the public key inside the issuer's own agent id. The counter is a single running number across every read nomankind has served, handed out by the database in one statement its single writer serializes — so two readers arriving in the same instant are handed two numbers, never one number twice — and still unique by index behind that. The receipt is stored before the response is sent, so a receipt in a reader's hands always has a row behind it; a request that dies between drawing its number and storing its receipt leaves a gap rather than a reused number, and the day's published `counter_first`, `counter_last` and `receipts` are what make that gap visible — the range minus the receipts issued is exactly the numbers drawn and never handed over. An entry that is not verified is 409 `entry_not_verified` with its `status` and `superseded_by`, and issues no receipt and moves no counter; an entry the log does not hold is 404 `not_found`, a subject search that nothing answers is 404 `no_entry`, an id that is not one is 400 `bad_id`, and a deployment with no receipt signer is 503 `receipts_not_configured` rather than an unsigned receipt.

The record is free, from the seal (decision D-127). `RELEASE_WINDOW_DAYS` in `src/policy.ts` is zero, and the rule it names is unchanged (decision D-100): an event is released that many days after the seal that covers it, an entry that many days after the seal covering its submission, computed from the seal's `sealed_at` and never stored — so at zero every entry's content is public, CC0 and in the daily mirror the moment it is sealed, served to anybody who asks with no key, no signature and nothing to pay. An entry nothing has sealed yet is not released at all, which is the one thing the number does not change. The proof was always public from the first minute and still is: every event's position, instant, type, entry id and both hashes, every seal, anchor and operator record, and an entry's id, domain, subject, category, status, effective tier, seal object, signers, the hashes inside its records, and its release date.

The window's code is dormant rather than gone, so a fork that wants one sets that one constant and gets it whole: 402 `unreleased` with `release_date` from `GET /read`, `{proof, sidecar, release_date}` instead of the entry from `GET /entries/{id}`, unreleased events as hash lines (`payload: null`, `withheld: true`) from `GET /events` — never the registry, whose six event types (`operator_registered`, `operator_trusted`, `operator_untrusted`, `agent_bound`, `operator_joined_domain`, `pool_snapshot`) are served in full the moment a seal covers them — a `GET /sync` page that stops at the released head while `sealed_head` still reports the true one, and 403 `unreleased` from `GET /captures/{hash}`. A bad key is still 401 `bad_key` and a signature that does not verify is still 401 `bad_signature`. The read count, the receipts and the counters are unchanged by any of it: a read is counted, a receipt is issued, and nothing anywhere is charged for.

The sweep publishes the counts. Each run, before it seals, appends one `read_count` event for every finished UTC day it has not published yet — `{date, reads: [{entry_id, count}], total, counter_first, counter_last, receipts}` — starting from the day after the last one published, or from the day of the oldest receipt when none ever was, and never past yesterday, because today is not over. A day inside that range that nobody read publishes a total of zero, so a reader checking their counters finds every day accounted for rather than a gap. `receipts` is how many receipts of either kind were issued that day — rows, where `total` is reads, because one sync receipt can be six reads or none — and it is what the counter range is held against: `counter_last - counter_first + 1 - receipts` is how many counters were drawn and never handed over. The ledger and the mirror ignore it; it is evidence about the receipts, not about money. The seal step runs after it in the same sweep, which is what makes each day's published count the number the seal commits to. A log that has served no reads publishes nothing at all. The payload's `duplicates` array names what the duplicate rule dropped that day (D-085): one row per entry whose sync reads were not counted because a newer live entry says the same fact, carrying that entry's id, the `newest` one the group's reads went to instead, and the `sync_reads` dropped — sorted by entry id, empty on a day nothing was dropped, so a contributor can see that a fact filed twice earned once rather than find the difference missing from the total.

`SEALING_AGENT_KEY` is nomankind's own agent and signs those receipts on every environment — the real sealing agent's key on production, where it also signs the seal fingerprint submitted to the founding registry, and a throwaway secret on demo. Locally, put `SEALING_AGENT_KEY=<private_key_pkcs8 from a keygen file>` in `.dev.vars`; without it the read routes answer 503 `receipts_not_configured`. Every optional binding has one absent value and not two: a var nobody set and a var set to the empty string are read the same way, so an unconfigured maintainer answers `POST /genesis` with 503 `maintainer_not_configured` rather than 403 `not_maintainer`, and `POST /entries` with 503 `fetcher_not_configured` rather than archiving a capture whose sidecar names nobody. The `ENVIRONMENT` var is a closed set — `local`, `demo`, `production` — and is checked ahead of every door, `GET /health` included: an unknown value is 503 `environment_misconfigured` with the value it was given, and the sweep does nothing but record that reason on every step so `/status` shows it, because the name silently chooses the adapters a deployment runs with, the witness among them, and a misspelling would otherwise have selected the mocks on a real deployment. And every response carries `Strict-Transport-Security: max-age=31536000` — pages, JSON and refusals alike, without `includeSubDomains` and without `preload` — beside the `X-Content-Type-Options`, `Referrer-Policy` and `Content-Security-Policy` the pages already carried.

Every one of them needs a key, and `npm run keygen -- [<name> | --out <path>]` is the only place one is made (D-016). The argument is a name rather than a path: the key is written to `~/.nomankind/keys/<name>.json`, `default.json` when no name is given, in a per-user directory created 0700 with the file 0600 — outside the working tree, so no `git add .` in a clone can commit a private key. It prints the path it wrote and the agent id, never the private half, and refuses a path that already holds a key with one named line and exit 1 rather than destroying a key somebody is using. `--out <path>` writes somewhere else when that is what you mean, and it replaces the name rather than joining it: the two together are refused with the usage line; the repository's `.gitignore` covers the usual key names anyway, because the cost of the one that slips through is a key nobody can withdraw.

Nine commands sit on top of those routes.

- `npm run submit -- <key.json> <base-url> <fields.json>` submits one entry. The fields file holds the eleven fields an author chooses — subject, category, domain, claim, before, after, effective_at, citation, and the nullable evidence, observation and supersedes — and naming any of the rest is refused as `bad_fields` before the network is touched. `domain` is required and has no default: the author names the domain they sign, so a file without one is `bad_fields` before the citation is fetched or the registry is asked. Naming any of the rest is refused the same way, because the id, the submission time, the norm version, the tier, the signature and the snapshot hash are the submission's to fill in and the author and its operator are the key's. It fetches the citation itself, hashes it under the norm rule in force, builds the core through the same kernel the Worker checks it with, signs it and posts it; the operator it names is the one the registry puts behind the signing key, which is null for a bare key. It prints the entry id and the status the log gave it, and exits 0 on 201, 1 on a refusal, 2 on a fields file it will not send. `--receipt <file.json>` carries the measurement receipt of an observed entry: the artifact is checked and hashed with the kernel's own `checkReceiptArtifact` and `receiptArtifactHash` before the network is touched, the hash fills `observation.receipt_hash` when the fields file leaves it null, and the artifact goes out as the body's `receipt`, which is what the door archives at that hash. `--transcript <file.json>` carries the frozen transcript of a behavior or misbehavior entry, whose snapshot is the artifact and not the cited page: it is hashed with the kernel's own `transcriptArtifactHash`, which refuses a shape that is not a transcript before anything is fetched, its six measured fields fill the `evidence` the fields file leaves null, and its hash is the `snapshot_hash` the author signs, which the door reaches again by rebuilding the same artifact from the same evidence and archives at that hash — so nothing is fetched and no second copy is sent. A fields file whose evidence names a transcript the file is not is refused in one line rather than posted, and a receipt and a transcript on one submission are a usage error: an observed entry carries a receipt and a transcript entry a transcript, never both. The fields file may also carry `disclosure`, which is not a core field and is never signed — `--disclosure <file.json>` is the same body field read from a file, and naming it both ways is a usage error: it goes out as the body's `disclosure`, where the door hashes each disclosed value against the placeholder it stands for.
- `npm run reconfirm -- <key.json> <base-url> <entry-id>` is the fixture reconfirmer. It reads the entry, fetches the citation itself, hashes it under the entry's `norm_version`, and signs the schema's `reconfirmations[]` item over its own hash. For a stated entry that hash is the whole attestation, so it reconfirms only when its hash is the entry's and otherwise stops with `snapshot_mismatch`, because a source that has moved is superseded rather than reconfirmed. For an observed entry outside behavior and misbehavior it reruns the entry's proposed test under the same allowlist and the same n-of-k rule the validator uses and signs a fresh measurement with its own receipt hash. A behavior or misbehavior entry needs a model rerun this fixture cannot make, so it stops with `cannot_reproduce`. On 201 it prints the refreshed `last_confirmed` and `expires_at`, rederived from the public log. It exits 0 on 201, 1 on any refusal including `entry_not_stale`, 2 on usage.
- `npm run validate -- <key.json> <base-url> <entry-id> [--assigned] [--duplicate-of <entry-id>]` is the fixture validator. It reads the entry, fetches the citation itself, hashes it under the entry's `norm_version`, and approves when its own hash is the entry's or rejects `snapshot_mismatch` when it is not. For an observed entry it judges the proposed test first (D-031): it accepts only the predicate forms it can actually decide against the capture — `contains:<text>`, `absent:<text>`, `status:<code>` — reruns an accepted one under the published n-of-k rule and records its own receipt, and does not accept anything else, which leaves the entry validated as a document. A behavior or misbehavior entry needs a model rerun this fixture cannot make, so its test is never accepted. `--assigned` claims the open draw; the Worker refuses a wrong claim. `--duplicate-of <entry-id>` skips the judgment of the snapshot entirely and rejects in the published duplicate form, the reason `duplicate_claim:<entry-id>`, which is how the fixture files the judgment case the submit door cannot decide for itself. It exits 0 on 201 and on a 409 `entry_closed` (expected for the third of three in a small pool), 1 on any other refusal, 2 on usage.
- `npm run read -- <base-url> <entry-id> [--key <secret>] [--sign <key.json>]` and `npm run read -- <base-url> --subject <subject> --category <category> [--domain <slug>] [--min-tier <tier>] [--max-age <days>] [--key <secret>] [--sign <key.json>]` is the frozen reader. `--key` reads on that key's tier and `--sign` signs the read with an operator's agent key; either decides the bucket the read is counted in, and neither is needed for the content, which is served to anybody from the seal. It fetches through the read routes in whichever of the two forms the arguments name, then checks what came back for itself: the receipt's signature against the key inside its own issuer id, the receipt's `entry_hash` against the hash it recomputes from the entry's core, and the entry's inclusion proof against the covering seal's root. It exits 0 when every check passes.
- `npm run export -- <base-url> <entry-id> <out-dir> [--bounded] [--key <api key>] [--sign <key.json>]` writes the two files the offline verifier takes: `entry.json` as the Worker serves it, and `log.json` as the log bundle beside it — the whole log paged to its head, the registry as the operator routes report it, and the captures the snapshot hashes point at. `--bounded` writes the second file bounded to this entry's seals instead, and reads as narrowly as it writes: one call to `GET /entries/{id}/events` answers this entry's own events with a proof each, and then the seals those proofs are against and the seal before each of them, and the same registry and captures. Neither the file nor the walk grows with the log — the same handful of requests on a log of a thousand entries as on a log of ten — and on a log of a few hundred events the bundle is around a twenty-fourth the size. What it costs is the four checks that are folds over the whole log: the chain, the exclusions, the derived view and the attestations, which the verifier names as not run rather than passing over. The record signatures are not among them — the door answers the entry's decisions, so they are checked exactly as on a full bundle. Full is the default, because an `ok` over the whole log is the wider sentence and the paper's two files are what the checkpoint and the published example carry. `--key` presents a key and `--sign` signs every read with an operator's agent key, either of which names who is reading and so which cap the reads are counted against; with neither, the export is the same record read on the free tier. Against a fork that publishes a release window of its own, either credential is also what reaches content that fork withholds, and with neither the export is the released view and says so on stderr. The two credentials are alternatives and presenting both is a usage error.
- `npm run checkpoint -- [--wait-seal] <base-url> <maintainer-key.json> <fixture-a.json> <fixture-b.json> <fixture-c.json> <out-dir> [--sign <key.json>]` walks the paper's first falsifiable milestone against a running Worker: three fixture operators join and are named to the trusted pool, the maintainer submits one seeded entry with a bare key, the three validate it, the entry comes back verified, the two files are exported, and `verifyOffline` answers ok on them. It prints the TXT record each fixture operator needs before registering it, one line per step, and a final line with the entry id and the verifier's verdict; it exits 0 only when every step held. `--wait-seal` adds one step before the export: it polls `GET /seals` every fifteen seconds, for one seal interval plus a minute, until the head seal covers the entry's newest event, so the two files carry the inclusion proof rather than a seal that is merely not made yet. `--sign <key.json>` signs every read the walk makes with an operator's agent key. The entry it just made is minutes old and is exported whole all the same, because a seal is all a release takes (D-100 at zero, D-127). Against a fork that publishes a window of its own, a free export of it is the released view, `verifyOffline` answers `entry_withheld`, and the verify step says so in one line — `withheld inside the release window; pass --sign <key.json>` — rather than printing a diff that means the same thing.
- `npm run mirror -- <base-url> <out-dir>` rebuilds the whole daily export — the `<env>/` directory of the log mirror — from an instance's public doors, byte-identical to what that instance pushed for the same sealed head. Exits 0, 1 on a named refusal, 2 on usage.
- `npm run verify-mirror -- <mirror-dir> [--captures <url-or-dir>] [--entry <id>]` checks one such directory end to end: the manifest, the event chain, every seal, every anchor, and every entry through `verifyOffline`. One line per item, one summary line; exits 0 when nothing failed, 1 on any failure, 2 on usage.
- `npm run import-mirror -- <mirror-dir>/<env> [--persist-to <dir>] [--captures <url-or-dir>] [--force]` replays one environment's export into the local D1 database `npm run dev` serves from, so a fork keeps going with the record: run it, then `npm run dev`, and the entries, operators, seals, anchors, attestations and standing answer that log while the sweep goes on sealing from the imported head. It runs `verify-mirror`'s own checks before it writes anything, appends the events under the same chain rule every door writes under, folds the registry rows out of them, and re-derives every entry with the kernel rather than copying one — a difference is a refusal. The persist path is the same one `wrangler dev --persist-to` takes, defaulting to the project's `.wrangler/state`, so the server reads what the import wrote. It prints one summary line and exits 0, 1 with the named refusal, 2 on usage. All three are the Mirror section below.

Every command that takes a base URL leaves the process the same way. A URL nothing answers is one line — `unreachable <base-url>: <cause>`, the cause being the errno the platform gave — and exit 1, rather than the undici frame and the absolute path of every file on the way down; any other error that escapes a run is one named line and exit 1 too. A usage error is one line and exit 2. Set `NOMANKIND_DEBUG=1` to get the stack printed after the named line, which is the only way to see one.

Two build commands write committed files that must not drift from their sources. `npm run gen:docs` reads `docs/FORK.md`, `paper/WHITEPAPER.md` and `paper/SUMMARY.md` into `src/ui/docs.generated.ts` and must be rerun whenever one of them changes, because a Worker has no file system to read a document from at run time; `test/docs-generation.test.ts` compares the committed module against a fresh generation, exactly as the validator below is compared. `npm run gen:validator` recompiles `src/schema-validator.generated.ts` from the entry schema and must be rerun whenever the schema changes: Workers forbid building a validator at run time, so the schema is compiled ahead of time and the committed file is checked against a fresh generation. And production has no maintainer key configured, so `POST /entries` there answers 503 `fetcher_not_configured` until M25: the sidecar names the 1F916 identity that fetched, and an unconfigured deployment has none to name.

## Disputing, revalidating, reporting

Three doors, one per way a verified entry can be questioned.

`POST /entries/{id}/dispute` is Section 6's challenge. The body is `{entry, receipt, from_report_seq, from_revalidation_seq}`, where `entry` is a full signed correction entry exactly as `POST /entries` takes one — the correction category, the target's subject, a citation, and the challenger as its author — and the two positions are optional. A challenge *is* an entry, so it goes through the submit route's own pipeline rather than a thinner copy of it: the author's signature, the kernel's submission and supersession checks, the citation fetched here under the norm rule and its hash compared with the one the challenger signed, and the schema over the derived correction. Filing takes a stake, and the stake is standing: `DISPUTE_STAKE_STANDING` from `src/policy.ts`, written as a ledger row in the batch that seals the filing. Contribution is the only currency here, so there is no fee to pay in anything else. On success the answer is 201 with `{correction, target}`, the correction `draft` and the target carrying its new `disputes[]` row with outcome `open`. Refusals are 400 `bad_id` or `bad_body`, 401 for a bad request or entry signature, 404 `not_found`, then 422 `self_dispute`: an author does not challenge its own entry, and the rule is put to the key that signed the envelope and to the author the correction names alike, before the door settles which of the two the filer is — asked the other way round it was a word the log could never say, because by then the two are the same key by construction. Then 403 `author_mismatch` when the signing key is not the correction's author, then every refusal `POST /entries` makes on the correction itself, then 409 `dispute_open` when one challenge is already open and 422 for `entry_not_verified`, `not_correction`, `missing_citation`, `subject_mismatch`, `bad_report_link` and `bad_revalidation_link`. A registered operator's filing is gated on standing at both doors: available standing — what the sweep last stored for it, less what its still-open stakes already hold — must cover `DISPUTE_STAKE_STANDING` here and `REVALIDATION_REQUEST_STAKE_STANDING` at the revalidate door, and a filer that cannot cover it is refused 422 `insufficient_standing` before anything is written, while a bare key has no standing to stake at all. Nothing is written and nothing is archived unless every check passes.

The challenge is then validated at `POST /entries/{id}/validate` like any other entry, with one extra exclusion: no operator that signed the original, submitter or validator, may judge it, and one that tries is refused 422 `original_signer`. The decision that verifies the correction is the same batch that seals `dispute_upheld` on the target, rewrites the target's row — `overturned`, with `overturned_by` naming the correction — and writes the refund and the reward; the decision that rejects it seals `dispute_failed` with the first rejection's reason and writes the forfeit. A reader never sees a correction verified and its target still standing.

`POST /entries/{id}/revalidate` is Section 6's other half: a check inside the window, asked for by staking standing. The body is empty, because no citation is needed and the signed request is the whole ask. Only an operator may — a bare key has no standing to stake, and gets 422 `bare_key` — and requests are capped per operator per window, measured from the entry's own `last_confirmed`. Refusals are 400 `bad_id` or `bad_body`, 401, 404 `not_found`, and then the check's own order — 422 `entry_not_verified`, `entry_stale` (a stale entry is reconfirmed, not rechecked), `bare_key`, `operator_not_in_domain`, `cap_exceeded`, 409 `request_open` while a check is already in flight, and 422 `insufficient_standing` when the stake is more than the requester's standing covers. The sweep draws the checker: a trusted operator, by the same public randomness and against the same committed pool snapshot as a validation draw, excluding the entry's own submitter operator and the requester's, with the same seventy-two hours and the same miss. The draws and the misses are in the sweep's report under `revalidation_drawn` and `revalidation_missed`; a miss closes the assignment and not the request, so the next run redraws.

The drawn checker answers at `POST /entries/{id}/revalidate/resolve` with `{record, signature, held}`, where `record` is the schema's `reconfirmations[]` item signed under `nomankind-record-v1` with the kind `reconfirmation` and `held` is the checker's verdict. `held` forfeits the requester's stake; `changed` returns it, and no reward beside it — a check that turns up a citation is upgraded into a dispute, and the reward is that dispute's. The status never changes here whichever way it went — revalidation confirms rather than overturns, and a fact that really changed is corrected by a superseding entry or by a dispute. Refusals are 400 `bad_id` or `bad_body`, 401, 404 `not_found`, 403 `agent_mismatch`, and 422 `no_open_request`, `deadline_passed` when the agent answering was drawn for the open request and the draw's window has run out — read off the draw the sweep wrote rather than off an assignment row the sweep has not closed yet, so a late check gets the same answer whether or not a sweep has run since — `not_assigned`, `bad_signed_at` and `bad_record_signature`.

`POST /entries/{id}/failure-reports` is Section 8's reader door, and any key may knock: the body is `{observed, artifact, citation}`, the artifact is frozen and hashed like any other — a transcript or a receipt, by its own key set — and archived at that hash before anything is written. A report never changes the core or the status by itself. What it can do is reach the threshold: a published number of distinct **verified operators**, counted against the registry at the position the question is asked, auto-opens a revalidation on the log's own initiative, with no requester, no operator and no stake. So three bare-key reports open nothing and three registered operators open one check, which is Section 12's answer to a flood — the cost is a wasted check and never a wrong record. The answer is 201 with `{entry, opened_revalidation}`. Refusals are 400 `bad_id` or `bad_body`, 401, 404 `not_found`, the artifact refusals (`unknown_artifact`, `transcript_shape`, `receipt_shape`, `unknown_method`, `billing_shape`, `redacted_load_bearing`), 409 `duplicate_reporter` for a reader filing twice, and 422 `entry_not_verified`, `empty_observed` and `bad_artifact_hash`. The archived artifact's sidecar names the identity that put it there, as a capture's does, so a deployment with no maintainer key answers 503 `fetcher_not_configured` here exactly as `POST /entries` does. A report that carries a citation is eligible for upgrade: its own reporter may file it as a dispute with `from_report_seq`, and the report's `upgraded_to` then names the correction. A revalidation request its own requester upgrades with `from_revalidation_seq` closes as `upgraded` in the same batch, so the request's stake comes back and the dispute's takes over.

Four commands sit on those doors.

- `npm run dispute -- <key.json> <base-url> <target-id> <fields.json> [--from-report N] [--from-revalidation N]` files one challenge. It reads the target for its subject, builds and signs a correction core with the submit command's own helper — the same fetch under the norm rule, the same kernel naming and stamping it, the same operator read from the registry — and posts it. The fields file holds the seven a challenger chooses: claim, before, after, effective_at, citation, the nullable evidence, and subject, which defaults to the target's; the category is always `correction`, so a file naming it is refused as `bad_fields` before the network is touched. It prints the correction id and the target's status, and exits 0 on 201, 1 on a refusal, 2 on usage.
- `npm run revalidate -- <key.json> <base-url> <entry-id>` asks for a check, posting the empty body the door takes. `npm run revalidate -- <key.json> <base-url> <entry-id> --resolve held|changed` is the drawn checker answering: it reads the entry, fetches the citation itself, hashes it under the entry's `norm_version` exactly as the reconfirmer does, and signs the reconfirmation record over its own hash. The verdict is the operator's, not the command's — a word that is not one of the two is refused rather than read as one of them, because it decides whose stake is forfeited. Exits 0 on success, 1 on a refusal, 2 on usage.
- `npm run report -- <key.json> <base-url> <entry-id> <report.json>` files one failure report. The file holds `observed`, `artifact` and an optional `citation`; the artifact is sent through untouched, because the hash the Worker takes is over exactly those bytes. It prints whether this report was the one that opened a check. Exits 0 on 201, 1 on a refusal, 2 on usage.
- `npm run register -- <key.json> <base-url> <operator-domain> [--domain <slug>] [--genesis <maintainer-key.json>]` walks the joining steps for one operator. It prints the TXT record the domain needs before anything is asked of the door, signs the independence attestation of the registered domain `--domain` names — defaulting to `ai-ecosystem` — with the operator's own key, and registers; an operator already there is reported and not treated as a failure. `--genesis` names it trusted with a second signed request under the maintainer's key, which is the only key that can. `npm run register -- <key.json> <base-url> <operator-domain> --join <slug>` is the other half: it signs that domain's own attestation and posts it to `POST /operators/{id}/domains`, which is how an operator already in the registry takes on a further domain. A domain the operator already holds is reported and not treated as a failure. Until the payment provider is wired it sends the mock adapter's own reference, which demo and local accept and production refuses outright with `payout_unavailable`. Exits 0 when every step held.

## Standing and contribution

Section 9's incentives, and both halves of the answer are recomputed rather than assigned. Since decision D-127 there is only one currency in this record: contribution, counted in standing. No read is priced, nothing is owed and no money moves anywhere, so the ledger holds stakes and the log's own reconciliations and nothing denominated in a currency.

**Standing** is a fold over the sealed log by a published formula, so anyone can recompute anyone's standing and get the same number. It is earned by completed validations (`STANDING_VALIDATION_VOLUNTEERED`, `STANDING_VALIDATION_ASSIGNED` for the drawn checker), beside them by a record carrying a passing measurement (`STANDING_VALIDATION_REPRODUCED`, counted as `validations_reproduced`), by an entry of yours first deriving verified (`STANDING_SUBMISSION_VERIFIED`), by a scored drift attestation (`STANDING_ATTESTATION_SCORED`), and by a challenge that holds (`STANDING_DISPUTE_UPHELD`). A revalidation request whose check found the fact changed returns the stake and earns the requester `STANDING_REVALIDATION_CHANGED` (D-095). It is burned by an overturned entry you signed — the author's operator, every approving operator, every reconfirmer, once each per entry (`STANDING_OVERTURNED_SIGNER`) — by a missed assignment or a missed revalidation (`STANDING_ASSIGNMENT_MISSED`), and by a stake that is forfeited: `DISPUTE_STAKE_STANDING` on a failed challenge, `REVALIDATION_REQUEST_STAKE_STANDING` on a check that held. An open filing or an open request *locks* its stake rather than spending it, so `standing` is earned less burned and `available` is that less what is locked. Decay is paused (`STANDING_DECAY_PAUSED`), so there is no decay term at all rather than a rate of zero. Nothing else in the log moves standing, and the amounts live in `src/policy.ts` and nowhere else.

Standing gates the trusted pool, and the sweep is what applies it: a registered, non-maintainer, non-provider operator that reaches `STANDING_TRUSTED_ENTRY` is trusted, and a trusted operator that falls below `STANDING_TRUSTED_STAY` is untrusted, each by an `operator_trusted` or `operator_untrusted` event whose operator row records `named_by: "standing"` — no key did it, the formula did. Those events are sealed by the next run, which is also the run whose pool snapshot picks them up.

**Measuring earns more than copying** (D-087, in standing since D-127). `STANDING_VALIDATION_REPRODUCED` is earned beside the amount a completed validation or reconfirmation earns, and only when that operator's own signed record carries a passing measurement under the n-of-k rule — so a validator that accepted the test without running it earns what a copier earns, and the trusted pool tilts toward the operators who measure. That is the whole of the difference: nobody is paid more, because nobody is paid.

**The read counts stay** (`read_count`, published daily by the sweep) and are evidence that the record is used rather than a bill: a reader can hold their own receipts against the day the log published, and a day where the two disagree is a day to ask about.

Two sweep steps do the work, after the seal and only over what the seal covers; before the first seal both refuse with `unsealed`.

- **Ledger.** From its `ledger` cursor to the sealed head it walks what the seal covers and writes the day's `reconciliation` row, which holds what the log published against the rows written for it, and prices the stake records a dispute or a revalidation opened and closed. Every row's id names the event that produced it, so a replayed cursor rewrites the same rows and changes nothing. A run walks at most `LEDGER_ENTRIES_PER_RUN` of a day's entries, and a longer day is resumed by the next run from the entry cursor beside the ledger's own, with the day's `reconciliation` row written only once every entry of it has been walked. The rows go to D1 in batches of at most `SWEEP_BATCH_STATEMENTS`.
- **Standing.** The fold runs forward from a cursor: every operator's accumulator and the position it covers are stored in `operator_standing` (migration 0017), and a run folds the sealed events after that position and continues the counts, so the stored answer is always what folding the whole log to the same position would give. The number is cached on the operator row with its position as before, and the trust changes above are appended. A missing or disagreeing cursor folds the whole log and writes one the next run can use, which is also what happens the first time — drop the table and the same numbers come back. The report carries `standing: {position, operators, trusted, untrusted}`.

Four JSON reads serve all of it, with `cache-control: no-store`, 405 on anything but GET, and 503 `storage_unreachable` like every other read route. They never negotiate HTML.

- `GET /standing` is every operator's standing as the sweep last folded it: `{position, formula, operators}`, highest first, with `formula` naming the policy terms the fold applied and `position` the position the sweep folded to, which is at or behind the sealed head. Every registered operator is on the list, and one registered since the last fold is on it at zero at that position — which is a different answer from being absent. The published number is the sweep's at its position; the recompute is `npm run standing`, which folds the log itself and is what settles a disagreement. Before the first seal, `position` is null and `operators` is empty, and before the sweep has ever folded, the log is folded here because there is nothing stored to serve. It takes no query, and neither do `GET /ledger`, `GET /operators/{id}/standing` and `GET /operators/{id}/ledger`: each answers one whole fold and has nothing to narrow, so any parameter at all is 400 `bad_query`.
- `GET /operators/{id}/standing` is one operator's, from the same stored fold: `{operator, position, earned, burned, locked, standing, available, counts, formula, stored}`, where `stored` is the cached column and the position it was written at, or null when standing has never been computed for it. An unregistered operator is 404 `not_found`, because an unknown name has no standing rather than a standing of zero.
- `GET /operators/{id}/ledger` is `{operator, balance, rows}` — the newest hundred rows and what they add up to at the moment of asking. Nothing in them is money: a row carries the unit it was put up in, and the only unit anyone puts up is standing.
- `GET /ledger` is the newest hundred daily `reconciliations`: each day's published read count against the rows written for it.

`npm run standing -- <base-url> <operator> [--sign <key.json>]` is the check an operator can make for themselves. It reads the sealed head from `GET /seals`, pages `GET /events` through it, folds them with the same kernel the Worker uses, and compares `earned`, `burned`, `locked`, `standing`, `available` and `position` with what `GET /operators/{id}/standing` answered. It prints one `ok` line when every field agrees and one line per field that does not, with both numbers; it exits 0, 1 on a disagreement or a refusal, and 2 on usage. Every sealed event goes out whole here, so an unsigned run folds exactly what a signed one does; `--sign <key.json>` signs the reads with an operator's agent key all the same, for the cap they are counted against and for a fork whose own release window would hand a free reader a hash line with nothing in it to fold.

## Attesting a model

Section 8's other half, and the one part of the record that is about a model rather than about a fact.

An attestation says one thing in public: as of this date, this model's beliefs about the AI ecosystem agree with the verified record to this degree, judged by parties its lab does not control. Nothing here is set by anyone. The questions are drawn by public randomness from the verified, observed, fresh entries, against a pool snapshot the log committed to before the beacon round that uses it — the same construction as validator assignment — so neither the model's operator nor the maintainer picks them. The scorers are drawn the same way, three of them, and the model's own operator and the maintainer operators are excluded from the draw; a model provider cannot be in the pool at all. Every field an attestation publishes is folded out of the four events that carry its id and is never written directly.

Three doors, all signed like every other write, all `cache-control: no-store`, all 503 `storage_unreachable` when D1 does not answer, and all 503 `chain_conflict` when three rebuilds in a row lose the log's next position to another writer.

- `POST /attestations` is the model asking. The body is empty, because there is nothing to ask for beyond the asking. The answer is 201 with the derived attestation: the probes as `{entry_id, entry_hash}` sorted by id, the `probe_hash` over them, the `pool_snapshot_seq`, `beacon_round` and `beacon_randomness` both draws were computed from, the three `scorers` in draw order, and the `deadline`, which is `ATTESTATION_WINDOW_HOURS` from the request and covers the answers and the scores alike. Refusals, in order: 400 `bad_body`, 409 `attestation_open` when this model already has one running or has already attested in this round, 503 `beacon_unavailable`, 422 `no_pool_snapshot`, 422 `snapshot_after_beacon` when the newest snapshot does not precede the newest round and the client should come back for a later one, 422 `insufficient_candidates` when the observed tier is thinner than `PROBE_SET_MIN_CANDIDATES`, 422 `empty_pool` or `insufficient_scorers` when the pool cannot field three eligible operators, and 422 `no_agent_for_operator` when the draw names a trusted operator with no agent bound under it, because the operator is the unit of the draw and the agent beside it is the first one bound.
- `POST /attestations/{id}/answers` is the model answering. The body is `{answers: [{entry_id, answer}]}`, one string answer per probe and exactly the probe ids. Only the hash goes in the log — the answers themselves are stored beside the attestation and served from there — so three scorers can prove they scored the same answers. Refusals: 400 `bad_id` or `bad_body`, 404 `not_found`, 403 `not_model`, 409 `not_open`, 422 `deadline_passed`, 422 `bad_answers`.
- `POST /attestations/{id}/score` is one drawn scorer's verdict. The body is `{record, signature}`, where `record` is `{agent, operator, agreed, probe_hash, answers_hash, signed_at}` and `signature` is the `nomankind-record-v1` signature over the attestation id, the kind `attestation_score` and the record — the attestation id sits in the entry id slot of the signing bytes, so a score signed for one attestation can never be replayed onto another and a validation can never be replayed as a score. Refusals: 400 `bad_id` or `bad_body`, 404 `not_found`, 403 `agent_mismatch`, 422 `bad_signed_at` outside `REQUEST_CLOCK_SKEW_SECONDS`, 422 `bad_record_signature`, then the kernel's own, in its order — 409 `not_open`, 422 `deadline_passed`, 403 `not_a_scorer`, 422 `operator_mismatch`, 403 `model_operator`, 403 `operator_not_in_domain`, 409 `duplicate_scorer`, 422 `probe_hash_mismatch`, 422 `answers_hash_mismatch`, 422 `bad_agreed`. The third score turns the status to `scored` and publishes `score` as `{agreed, probe_count}` — the median of the scorers' counts, out of how many probes were asked, never a bare fraction — with the UTC `date` the last score landed.

The sweep closes the ones nobody finished. Before it seals, each run appends one `attestation_expired` for every attestation still open or answered past its deadline, naming the scorer operators that never scored, and the report carries `attestations: {expired}`. An expiry is not a failing score and claims nothing about drift: a model whose scorers went quiet has not drifted, it has not been scored, and its operator asks for a new one.

Four reads serve the rest, JSON only.

- `GET /attestations?model=&operator=&before=&limit=` is a page of attestations, newest request first, keyset by `requested_seq`.
- `GET /attestations/{id}` is one, the derived record plus the `answers` the model gave.
- `GET /operators/{id}/attestations` is `{as_model, as_scorer}` — what an operator's own model asked for, and what it was drawn to judge — two lists because they are two different relationships.
- `GET /entries/{id}/confidence-inputs` is Section 8's confidence field, and `confidence` is null. So is `formula`: conf-v1 is unpublished on purpose, because a bad formula would be the most damaging thing in the system and there is nothing to calibrate one against yet. What is served instead is every input raw — `evidence_tier`, `effective_tier`, `test_verdict`, `test_acceptance`, the reproduction, observation and reconfirmation `counts`, `age_ratio` as days against the window rather than as a ratio, `stale`, `dispute_count`, `report_count`, `duplicate_of` and `duplicate_rejections` (the entry a validator's published `duplicate_claim` reason named, and how many rejections carry it), `superseded`, `overturned`, `status` — so a learner can build its own weighting from the receipts. 404 `not_found` for an entry the log does not hold.

`npm run attest -- request <key.json> <base-url> [--sign <key.json>]` asks for a probe set and prints the attestation, the probe and scorer counts, and the deadline. `npm run attest -- answer <key.json> <base-url> <id> [--answers <file.json>] [--drift] [--sign <key.json>]` answers it: with no file this fixture answers each probe with the cited entry's own `claim`, read from the Worker, which is a model in perfect agreement, and `--drift` answers every probe with `drifted`, which agrees with nothing. `npm run attest -- score <key.json> <base-url> <id> [--sign <key.json>]` is the fixture scorer: it reads the attestation and each probed entry's claim, counts a probe agreed when the answer and the claim are equal under `normalizeText` — a difference in whitespace or unicode form is not drift — signs the record and posts it. All three exit 0 on success, 1 on a refusal, 2 on usage. The answer and the score read each probed entry's own claim, and a claim inside the release window is not served to a free reader (D-100), so `--sign <key.json>` signs those reads and an unsigned run that meets a withheld entry stops with `withheld inside the release window; pass --sign <key.json>`. It is named separately from the key that signs the records the command posts, even when they are the same file, because a command that quietly borrowed one for the other would never say which.

## Syncing

`GET /sync` is Section 8's other door: the delta stream a continual learner resumes from. `?from=<seq>` is the sealed position to start at, inclusive, and defaults to the beginning of the log; `?limit=<n>` bounds the page at the same hundred every listing here is bounded at; `?flatten=true|false` collapses supersession chains; `?min_tier=stated|observed` is the trainer's evidence demand; `?min_source=official|recognized` is its demand about where the fact came from, compared against the class the sidecar derived from the entry's own citation; `?domain=<slug>` streams one registered domain, and absent is every domain. A query is refused rather than quietly narrowed: 400 `unknown_parameter`, `bad_from`, `bad_limit`, `bad_flatten`, `bad_min_tier`, `bad_min_source`, `unknown_domain`, in that order, and a parameter given twice is its own refusal, because two values are two questions and picking one of them is guessing. Anything but GET is 405.

The answer is `{from, head, sealed_head, as_of, seals, events, receipt}`. The stream is strictly by sealed position and stops at the last seal: `sealed_head` is that seal's `last_seq` and `as_of` is its `sealed_at`, and events the log has appended since are never delivered, because an unsealed event has no inclusion proof and a trainer handed one would hold a fact it cannot check. `head` is the last position this page accounts for — the smaller of `from + limit - 1` and the sealed head, whether or not every event in that stretch survived the filters — so the next sync starts at `head + 1`. A log with no seal yet, or a `from` already past the sealed head, answers `head: null` with no events and no receipt, and the trainer resumes from exactly where it was. Every entry in a page is re-derived at `sealed_head` rather than as it stands now, so two trainers resuming from the same `from` are handed the same page forever.

Each item in `events` is `{seq, kind, event, proof, entry, sidecar, entry_hash}`. `event` is the event record exactly as `GET /events` serves it, hash chain and all; `proof` is `{seal_seq, inclusion_proof}`, recomputed over the covering seal's own event range and verified against its root before it is served, exactly as `GET /events/{seq}/proof` does. `kind` is one of three. An `entry` item carries a fact to learn, with the derived entry record, its sidecar and its core hash beside it; an `unlearn` item is an upheld dispute, delivered so a trainer that already ingested the entry is told the log now says it was never true rather than merely ceasing to hear about it, and carries the same record with `status: "overturned"` and `overturned_by` set; an `event` item is everything else the log recorded — a registration, a pool snapshot, a day's read counts — and its `entry`, `sidecar` and `entry_hash` are null. The schema's `confidence` field travels inside the entry record, null as everywhere else. `seals` lists the seal records the delivered items point at, in seq order, with the `seq`, `root`, `hash`, `sealed_at`, `witnesses` and `registry` that `GET /seals/{seq}` serves, which is what those proofs recompute against.

The domain filter is the one filter an unlearn is subject to, and for the reason the others are not: an entry of another domain was never delivered to this trainer, so being told it was overturned is noise about a fact it does not hold. An entry sealed before schema v0.7 carries no `domain` at all and is streamed as `ai-ecosystem`, which is what it was signed as. The head advances past every dropped item, so a filtered stream resumes exactly where an unfiltered one would.

The other two filters only ever narrow entries. `flatten` drops a superseded entry, because the newest entry of the chain is delivered instead and its signed core's `supersedes` keeps the chain reachable; `min_tier` drops anything not verified, and anything whose effective tier — what it actually verified at, never what its core claimed — does not meet the demand. Neither can touch an unlearn or an event item: filtering an unlearn would leave a trainer holding a fact the log has withdrawn, which is the one failure the delta stream exists to prevent.

`receipt` is one signed sync receipt covering the whole page: `from`, `head`, `entries` (the distinct entries delivered, in first-delivery order, each with `entry_id`, `entry_hash` and `status`), `event_count`, `issued_at`, `counter`, `issuer`, `signature`. One receipt rather than one per entry, because a trainer syncing a page is having one conversation. Verify it with `verifySyncReceipt` from `src/receipt.ts`: Ed25519 over `nomankind-sync-receipt-v1\n` and the RFC 8785 canonical JSON of the seven fields, checked against the public key inside the issuer's own agent id. The counter is the same running number the read receipts carry, shared across both kinds, so a trainer and a reader can place their receipts in one stream of everything nomankind has served. The receipt is stored before the response is sent; a page on which every item was filtered issues no receipt and moves no counter, because nothing was served. A deployment with no `SEALING_AGENT_KEY` answers 503 `receipts_not_configured` before it reads anything. The counter is drawn before the receipt is signed and drawn once, in the single statement the read door draws it with, so a page is never refused for a number another isolate was holding; 503 `receipt_conflict` is now only the unique index refusing a row the counter says should not exist, and it is answered rather than signed around, because a receipt whose number is a guess is worth nothing.

Each delivered verified entry counts as one read. The day's `read_count` event is the union of the read receipts and the verified entries inside that day's sync receipts, grouped and summed together, so a trainer can check the receipts it holds against the published count. Nothing is charged for any of it: the count is evidence the record is used. An overturned or superseded entry in the same page is delivered but not counted: the log is telling the trainer to stop believing something, and counting its own correction would count one mistake twice.

`npm run sync -- <base-url> [--from N] [--limit N] [--domain <slug>] [--flatten] [--min-tier T] [--key <secret>] [--sign <key.json>] [--twice]` walks the stream from the command line and checks for itself what came back. Without a credential the page stops at the released head and its receipt says so; `--key` and `--sign` reach the sealed head, and they are alternatives rather than a pair.

## Free access: caps, keys and alerts

Whitepaper Section 9: "The log is free to read at low volume, forever." Decision D-127 made that the whole of it — the record is free from the seal, and nothing about it is sold. The free tier needs nothing: no key, no account, no header, a published cap per UTC day counted against the address a request came from. Three published numbers bound it, all of them in `src/policy.ts` and on [`/policy`](https://demo.nomankind.ai/policy): `RATE_TIERS.free.reads_per_day` is one client's day, `FREE_READS_PER_DAY_GLOBAL` is the whole log's free tier across every client together — checked before the per-client cap, counted in a scope of its own, refused with `"scope": "global"` in the 429 body — so a crowd of addresses each inside their own cap cannot be the whole day's budget, and `OPERATOR_READS_PER_DAY` is the bucket a registered operator's signed reads are metered in, keyed by operator id and answered with `x-nomankind-tier: operator`, so a validator walking the log spends its own day rather than the free tier of the address it came from. The ceiling bounds the free tier and nothing else: a key is never refused because strangers were reading. `GET /events` is a read like any other and is charged one unit per page against the caller's own bucket; `GET /events/{seq}/proof` and the entry's own page are not, because proof is public from the first minute.

A key is a **free identity** and not a purchase. It costs nothing, it buys nothing, and it grants no power over the log: every door a key opens is a door the free tier already opens more slowly, and nothing a key holder can do changes what the record says. What it is good for is being named — a cap of its own instead of the address it came from, receipts that carry `key` and `key_counter`, a usage listing, and webhook endpoints that have to belong to somebody. `POST /keys/free` issues one: no body, no provider, one key per client address per UTC day (429 `key_today` past that), and the secret is shown **once**, in that answer, because the table holds only its SHA-256 and there is no door that can show it again. A holder who loses one asks for another tomorrow. `GET /keys/tiers` is the tiers, unauthenticated: each with its name, its daily cap and whether it takes a key. A tier is a daily cap and nothing else.

Four doors of the paid loop are retired and answer 410 `{"error":"retired"}`: `POST /keys/checkout`, `GET /keys/claim`, `POST /keys/me/portal` and `POST /stripe/webhook`. They keep their addresses and their method checks, and each touches no storage and reads no secret on the way to that answer — a caller that integrated against one is owed the reason it stopped rather than a 404 that reads like a typo.

The key travels as `Authorization: Bearer nmk_<43 characters>`, and `npm run read` and `npm run sync` take it as `--key <secret>`. That is the only form accepted: a header with another scheme, or with no scheme at all, is 401 `bad_key` rather than read as a bare secret, so there is one documented wire format and not a second one nobody could withdraw. Every served response carries `x-nomankind-tier`, `x-nomankind-limit` and `x-nomankind-remaining`. A key is refused in one word, in the order the gate checks it — 401 `bad_key` before the database is touched, 401 `unknown_key`, 402 `key_canceled`, 402 `key_past_due` — the last two left over from the paid loop and unreachable for a key minted free, which is active from the minute it is made. Past the cap the answer is 429 `rate_limited` with the tier, the limit, what was used and `resets_at`, plus `retry-after` in seconds. A door charges after it has served, never before, so a refusal costs nothing and a delta page that crossed the cap is delivered rather than half-built.

A keyed read's receipt carries `key` — the key's public id, never its secret — and `key_counter`, that key's own running number, beside the log-wide `counter` every receipt has always carried. Both are null on a read made with no key, and a receipt issued before M24 carries neither property at all and verifies exactly as it always did: the signing bytes cover the two fields only when the object has them, so every stored receipt and every older fixture still checks out. Two counters rather than one, because a holder must be able to say "I hold reads 1 through n of mine" without knowing what anybody else read. `GET /keys/me` is the key itself, `GET /keys/me/receipts` pages its own receipts in its own counter order, and `GET /keys/me/usage` puts the two records side by side: `reads` is the quota counter the cap was enforced against, and `published` is the sealed `read_count` event for that day, which is the evidence of use the log publishes. That is the check Section 9 asks readers to make — "any reader can compare the receipts they hold against the published counts" — and a day where the two disagree is a day to ask about.

Change alerts are webhooks over sealed history. `POST /keys/me/webhooks` takes `{url, domain?, subject?, category?, kinds?}` and answers the endpoint with a shared secret shown once; the filters are matched on equality and a field left out means "any". The URL rule is checked before anything is stored — https only, a hostname with a dot, no credentials, no localhost — because this is a URL the Worker will knock on. One key holds a published number of live endpoints; a further one is 409 `endpoint_limit`, `DELETE /keys/me/webhooks/<id>` frees a slot, and `GET /keys/me/webhooks/<id>/deliveries` says what happened to every attempt. These are a holder's own subscription pages rather than reading doors, so they check identity and nothing else — 401 `missing_key`, `bad_key` or `unknown_key` — and the daily quota is never charged either, because an endpoint is not a read. The kinds are `submitted`, `verified`, `rejected`, `reconfirmed`, `superseded`, `overturned` and `stale`, and each is a moment already in the log, so an alert is a notification of something public and never a fact of its own. `stale` is the only one no event carries — a freshness window closing is a fact about the calendar rather than something anybody signs — so the sweep marks the entry and the alert step tells whoever subscribed in the same run, with the entry's own submission as `seq`, the seal covering that position, and the entry's `expires_at` as `at`; its delivery id is derived from the entry, that day and the endpoint rather than drawn at random, so a rerun tells nobody twice. Nothing is sent until a seal covers the event: the body carries that seal's `seq`, `root` and `sealed_at`, the event's position, the entry's hash, and the paths to the entry and to its inclusion proof, so a subscriber woken at three in the morning can check the claim rather than take this Worker's word for it.

Every delivery is signed with the endpoint's own secret, in the same header shape a payment provider's webhooks use, so a subscriber that already verifies one has a verifier for this. The request carries `content-type: application/json`, `x-nomankind-alert` (the delivery id), `x-nomankind-kind`, and `x-nomankind-signature: t=<unix seconds>,v1=<64 hex>`. To check it: take `t` from the header, join it to the **raw** request body with a single `.`, take the HMAC-SHA256 of those UTF-8 bytes under the endpoint's secret, and compare the lowercase hex against `v1` in constant time. Verify against the bytes that arrived and never a re-encoding of the parsed JSON, and check that `t` is recent — the timestamp is inside the signature, so a delivery captured off the wire cannot be replayed later under a fresh one. Any 2xx is delivered; anything else is one more attempt, retried on the published ladder in `src/policy.ts` and then marked failed rather than retried forever. A failed delivery is the endpoint's problem and never the log's: nothing about the record depends on an alert arriving. One run of the step derives alerts from at most `ALERT_EVENTS_PER_RUN` sealed events past its cursor, writes their deliveries in batches of at most `SWEEP_BATCH_STATEMENTS`, and posts at most `ALERT_DELIVERIES_PER_RUN` due deliveries, oldest first, so a host that never answers cannot hold a run for everybody else. An endpoint whose last `ALERT_ENDPOINT_TIMEOUTS_TO_DISABLE` deliveries all timed out is turned off: its pending deliveries are failed with `endpoint_disabled` rather than posted, and `GET /keys/me/webhooks` carries `enabled: false` on it — a derived field like every other, recomputed from the delivery records — so its holder can see why it went quiet.

## Browsing

The same Worker serves the log to a browser. `/` is the home page, with the counters and the latest sealed entries; `/entries` is the dense listing, narrowed by `category`, `status`, `domain`, `source`, `tier` and `fresh`, and paged by `before=<position>`, which is a plain decimal position — no sign, no padding, a safe integer — so `?before=0099` and `?before=1e9` are both 400 `bad_before` rather than two more spellings of one page — every row reads its entry's registered domain in a column beside its category, on every page and under every filter, because the chips are the filter and the column is the reading (D-125), and the home page's newest-sealed table carries the same column; the listing is an HTML page and nothing else, so it answers HTML whatever the `Accept` header says and takes no `limit` (a parameter it does not have is 400 `unknown_parameter`), and a program that wants records asks `GET /entries/{id}`, `GET /entries/{id}/events` or `GET /events` instead; `/entries/{id}` is one entry with every input the offline verifier takes — the signed core and its hash, each approver's own snapshot hash and evidence, the events in seq order, and the covering seal with its inclusion proof, position and witnesses — so a reader can check the entry from the page rather than taking its word for it. `/operators` and `/operators/{id}` show the registry, its trusted pool and each operator's validation record, with a co-signing view beside it: the directory carries one column for how many distinct operators each has signed an entry beside, and an operator's own page breaks that down pair by pair — the entries both signed, how many they agreed on and how many they opposed, newest pair first, each with a link to the newest entry the two share — all of it folded from the sealed `validation` and `reconfirmation` events by the sweep's counters step and served from the stored rows, so no view of it walks the log. `/policy` prints every published number grouped and read straight from `src/policy.ts`, alongside the rows the paper names and nothing publishes yet; `GET /policy` with `Accept: application/json` answers the same object as JSON, from the same module the kernel reads. `/api` documents every endpoint that exists, its parameters, what it answers and its refusals in check order, plus the write authentication rule and the endpoints later milestones bring. `/genesis` carries the call for founding trusted operators, the three joining steps, the attestation verbatim, and whoever has registered on this environment. `/dry-run` is the step-by-step guide to practicing those joining steps and one validation on demo — the key, the TXT record, the registration, one judged entry, the log, and the offline check — before the dry run that counts. `/how-it-works` walks the whole pipeline in ten panels — submit and snapshot, validate, seal and witness and anchor, read with a receipt, keep it true, standing and contribution, attest a model, verify offline, mirror and fork, free access and caps and alerts — and puts this environment's own newest record under each one, so every stage links to the log rather than to a description of it. `/independence` publishes the two sets the seal's independence rests on — every registered operator with its domains, the pinned witnesses with the head each countersigned on the newest seal, the intersection of the two (empty by rule: no pinned witness may be an operator of the record), and one row per signature kind saying what object it covers — with `GET /independence` answering the same report as JSON. `/domains` is the registry in one page: what a domain is, and for every registered one the tables it publishes — its categories, how long each stays fresh, which carry a transcript, who is too close to judge, how a subject is named, what may be cited, and the attestation an operator signs to join — read from `src/policy.ts` where the page is rendered, with this environment's own entry and trusted-operator counts beside each. `/docs` is everything written about the record in one place — the pages above grouped as read the record, join, and take it with you — and the three documents this Worker serves from the repository's own bytes are under it: `/docs/fork` is [`docs/FORK.md`](docs/FORK.md), `/docs/whitepaper` is [`paper/WHITEPAPER.md`](paper/WHITEPAPER.md) and `/docs/summary` is [`paper/SUMMARY.md`](paper/SUMMARY.md), each rendered as it is written, with a strip of its own headings across the top, so nothing about the design lives only on GitHub. `/status` is the pipeline's lights, one per stage (`STAGE_COUNT` in `src/status.ts`): each is a published rule applied to the log and to the report the sweep stored at the end of its last run, with the rule and the evidence beside every one, so nothing on it is probed when the page loads and nothing on it can be warmed by asking. `GET /status` with `Accept: application/json` answers the same object — as_of, counters, the stages, the stages that run only when someone asks, and the two thresholds the lights are decided by — and is cached at the edge beside the page, so either twin may be up to a minute behind the log. A stage whose sweep step threw reads failing with the thrown error named in its line, whatever its own facts say, until that step runs clean: a run that fell over inside the seal step is the one thing a board of derived facts alone could never show. `/mirror/latest` is the mirror page, and `/mirror` is a permanent redirect to it with the query kept, because a 404 on the parent of a page that exists is a dead end this route put there itself. `/landing` is the apex page, which is what nomankind.ai itself serves. www.nomankind.ai serves nothing of its own: every request on it answers a permanent redirect to nomankind.ai with the same path and query, so the landing page has one canonical host.

On the paths that answer both, the browser gets HTML and everyone else gets JSON: the decision is the request's `Accept` header, and both variants carry `vary: Accept` so no shared cache ever hands an agent a web page. The pages are cached at the edge for sixty seconds (`public, max-age=60, stale-while-revalidate=300`, the two numbers in `src/policy.ts`), keyed by host, path, query and which of the two documents the path answers, so a page may be up to a minute behind the log and a hundred readers cost it what one does; `GET /policy`, `GET /status` and `GET /independence` are cached with them — one a frozen module constant, the other the same reading of the same stored rows the page is rendered from — and every other JSON door is `cache-control: no-store` and never cached, so an agent that asks is answered from the log as it is this second. A request carrying a key or an agent signature is neither served from that cache nor stored in it: what it is answered depends on who is asking (the release window). Every read door answers a `HEAD` exactly as it answers the `GET` — the same status, the same headers, no body — and names `GET, HEAD` in its `Allow`; a wrong method is 405 with `Allow` and `{"error":"method_not_allowed"}` whether the path answers a page, an endpoint or both, and only a path nothing answers is `{"ok":false,"error":"not_found"}`. Pages are served under a strict content-security-policy — `default-src 'none'` with no script source named at all — because this UI has no client-side script of any kind; the look is classes in a stylesheet served from the Worker at `/static/app.css` and `/static/landing.css`, never an inline `style` attribute. Fonts come from Google Fonts, the only two external hosts the policy names, and every family is declared with a system fallback stack, so a page whose fonts were blocked is still a page that reads.

Four files sit beside the pages for whoever indexes them. `/robots.txt` opens the log to crawlers and names the sitemap of the host it was asked on, except on demo, which disallows everything: demo is a rehearsal with throwaway keys, and a search result pointing at it would be a copy of the record that is not the record. `/sitemap.xml` is the sitemaps.org urlset — on the apex, the landing page alone, because the apex has one page; on the app, the static pages, then every registered operator, then the newest entries with the date each was submitted as `<lastmod>`, never more than `SITEMAP_MAX_ENTRIES` of them (`src/policy.ts`, on the policy page with every other published number), read in keyset pages so a growing log costs a bounded document rather than a scan. Once that walk comes back full the same path answers a `<sitemapindex>` instead, because a bounded document that quietly stopped naming the rest of the log would be a record with an unlisted majority: it names `/sitemap-pages.xml`, which is the static pages and the operators bounded exactly as before, and one `/sitemap-entries-<k>.xml` per fixed range of the event sequence space, page `k` holding the entries submitted at positions `[(k-1) * SITEMAP_MAX_ENTRIES, k * SITEMAP_MAX_ENTRIES)`. The range is the sequence space rather than a count of rows, so an entry never moves to another page however many are submitted after it and there is no offset to page by; a range nothing has been submitted in yet is an empty urlset rather than a 404, and the pages are read in keyset pages under the same bound. `/robots.txt` names `/sitemap.xml` and nothing else, which is the one address a crawler needs. `/favicon.svg` and `/favicon.ico` answer the same drawn SVG — a rounded near-black square with a teal lowercase `n`, in the stylesheet's own two colours, with no external reference of any kind — under the stylesheets' hour of public cache; all four are cached at the edge like the pages. Which host a page calls its own is `APP_HOST`, a var set to `demo.nomankind.ai` on demo and `app.nomankind.ai` on production and to nothing locally: every page's `<link rel="canonical">` and the sitemap's absolute URLs are built on it, so a preview hostname and the real one are one address to an indexer rather than two, and the landing served at the apex's root is canonical at the apex instead. Every HTML answer also carries a `Link` header preloading the stylesheet that page links — the same versioned href as in the document, `/static/landing.css` for the landing — and opening a connection to Google Fonts, the one external origin the content-security-policy names; the not-found page carries it too, because a reader who mistyped an address is looking at a page like any other and should not wait longer for it.

## Mirror

Whitepaper Section 11: the sealed log is exported once per UTC day to [nomankind-ai/log](https://github.com/nomankind-ai/log) under CC0, so that nomankind going away is an inconvenience rather than an ending. The export is a step of the same sweep that seals and anchors, it runs on that one timer, and it pushes only what is sealed — the mirror is the sealed record, and an entry whose submission no seal covers is not in it. The day is claimed before the push, not after it: the `mirrors` row for the day is written `pending` when the export starts and updated to `pushed` with the commit when it lands, so a run killed mid-export is retried by the next run and not by every run of the day. A pending claim younger than one sweep interval makes the next run stand down (`mirror_pending`); an older one it takes over. A failed push leaves the row pending with its reason in the report, and the day counts as exported only once a row says `pushed`. The entry files are built from the stored derived rows wherever the row was derived over the world the sealed head holds, and re-derived from the events only for a row that is behind, so an export costs the pages it reads rather than a derivation per entry. Whatever this environment's directory no longer writes is deleted in the same push, so a file the layout has stopped producing does not linger in the mirror.

The repository holds one top-level directory per environment, `demo/` and `production/`, and each is a complete, self-contained export of that log's sealed state: `mirror.json` (the manifest — format, environment, `exported_at`, `as_of` and `head` from the newest seal, the counts, the schema and norm versions, the registered domains, `captures_base`, and the verify command), `events/<seal seq, 8 digits>.jsonl` (the events one seal covers, immutable once written), `seals.jsonl`, `anchors.jsonl`, `operators.json` (everything the offline verifier's registry needs), `entries/<entry id>.json` (`{entry, sidecar, entry_hash}` derived at the sealed head, exactly as `GET /sync` produces one) and `index.json` (one row per entry in submission order). The manifest's `format` is `nomankind-mirror-v3`, which is the layout as the release window made it — released events in full, unreleased ones as hash lines, an entry file only once its submission has opened, and a `release_date` on every index row — and both `nomankind-mirror-v2`, the whole sealed log as it was before the window, and `nomankind-mirror-v1` — a copy pulled before the attestations, the standing, the ledger and the sidecar's `source` joined the export — are still verified and imported as what they were, because a copy in somebody's hands is their exit and taking it back is not on offer. Every JSON document is two-space indented with a trailing newline and every `.jsonl` file is one compact document per line, so two exports of the same sealed head are byte-identical and a diff in that repository's history is a change in the log rather than in the formatting. The snapshots themselves are not in the mirror, only their hashes: the captured bytes are a third party's, they are served from each environment's own `/captures/{hash}`, and a withdrawal removes a copy while the proof stays.

`GET /mirror/latest` answers where an instance's newest export landed — the repository, the branch, the directory, and, when there is one, `{date, exported_at, commit, tree, head, seal_seq, entries, files_changed, url, raw_url}`; a browser gets the same thing as a page. It answers 404 `no_export` with the reason `mirror_not_configured` or `no_export_yet` until the first export lands.

Three commands sit on top of that. `npm run verify-mirror -- <mirror-dir> [--captures <url-or-dir>] [--entry <id>]` checks a fresh clone end to end: `mirror.json` against the files that are there, the event chain over every events file in seq order, every seal against the events it names and the seal before it, every anchor against that day's roots, and then every entry through the same `verifyOffline` the paper's two files and one script run. Every entry file, legacy or not, has its `entry` and `sidecar` re-derived from the mirror's own events at `as_of` and diffed field by field, its `entry_hash` recomputed, its `index.json` row rebuilt, its core checked against the core the log sealed and the author's signature checked over it; `verifyOffline` runs on top of that for a v0.7 entry. It prints `ok <id>`, `legacy <id>` for a record sealed under schema v0.6 — never `ok`, because v0.7's rules cannot be applied to bytes that never claimed them, but checked for its core, its signature, its derivation, the chain and the seal all the same, and a failed check on one is a failure like any other — or `FAIL <id> <check> <field> <reason>`, one line per difference, then one summary line; it exits 0 when nothing failed, 1 on any failure or an unreadable directory, 2 on usage. The captures come from `mirror.json`'s `captures_base` unless `--captures` names another origin or a local archive, which is one file per capture named by the hex of its hash with an optional `<hex>.meta.json` beside it. And `npm run mirror -- <base-url> <out-dir>` rebuilds the whole `<env>/` directory from the public API of any instance, so nobody has to believe the published export: both paths hand the same input to the same builder, and for the same sealed head `diff -r` is silent. The sealed head is pinned from the seal chain before anything else is read, and an instance that seals again mid-read stops the command with `head_moved` rather than mixing two moments into one directory.

The third is the exit itself. `npm run import-mirror -- <mirror-dir>/<env> [--persist-to <dir>] [--captures <url-or-dir>] [--force]` replays one environment's directory into the local D1 database `npm run dev` serves from — miniflare's, under the project's `.wrangler/state` unless `--persist-to` names another directory, which is the same persist path `wrangler dev --persist-to` and `wrangler d1 ... --local --persist-to` take, with the migrations applied first — so `npm run import-mirror -- ../log/production` and then `npm run dev` is that record running on your laptop: the entries, operators, seals, anchors, attestations and standing answer what the exporting instance answered, and the sweep goes on sealing from the imported head, so your first new event is sealed by the seal after the last one in the mirror, chained to it by `prev_hash`. Nothing is taken on trust: the command runs `verify-mirror`'s own checks first and writes nothing if any fail, the events go in through the same chain rule every door writes under, the registry rows are folded out of the events and held against `operators.json`, and every entry is re-derived by the kernel over the events just imported and compared with the mirror's file — a difference is a refusal, never a row. Only the seals, the anchors and the model's answers are stored as they stand, because a signature, an external timestamp and a thing a model said are not functions of the log. `--captures` is passed to the verification, so a fork with no network imports against a local capture archive; `--force` allows a database that already holds a log and still refuses one whose head is not a prefix of the mirror, importing only the tail so a fork catches up from a newer export. It prints one summary line — events, seals, anchors, operators, entries, attestations, ledger rows, the head and the newest seal — and exits 0, 1 with the named refusal, 2 on usage. The payout references are not in it and cannot be: they belong to a payment provider rather than to the log, and nothing pays against them here — the record is free and there are no payouts (D-127). [docs/FORK.md](docs/FORK.md) walks the whole exit, including moving the imported database to a remote D1 with `wrangler d1 export --local` and `wrangler d1 execute --remote --file`, which is wrangler's doing and not this command's.

The push is authenticated by a GitHub App, which is the primary credential because it does not expire: an export that stops because nobody renewed a secret is an outage with nothing wrong behind it. Create a GitHub App with **Contents: read and write** on the log repository and no other permission, install it on that repository alone, and set `MIRROR_APP_ID` and `MIRROR_APP_PRIVATE_KEY` — the `.pem` GitHub downloads once, read as PKCS#1 or PKCS#8 and in whichever shape it survived the paste — as Worker secrets. The adapter signs a short-lived JWT with the key, mints an installation token scoped to that one repository at the start of each push, and lets it die with the push. `MIRROR_TOKEN`, a personal access token with push access, is the fallback and is read only when the two App secrets are not both set; the move from one to the other is: set the App secrets, watch one export land, delete the token. Neither credential is ever logged, returned, or put in a refusal's detail — a mirror that named its own token in an error message would publish it.

[`docs/FORK.md`](docs/FORK.md) is the full version: what to clone, the layout in detail, how to verify, the capture archive's naming, what running your own instance takes, and the legal posture.
